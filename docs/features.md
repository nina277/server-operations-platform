# 機能一覧

実装済みの機能を、画面・API・安全機構の順にまとめる。

**「できないこと」も併記する。**何を意図的に実装しなかったかは、
何を実装したかと同じくらい設計の説明になるため。

設計の背景は [design.md](design.md)、
個々の判断の経緯は [backlog.md](backlog.md) にある。

## 2. 認証・認可

### 認証

| 機能 | 内容 |
|---|---|
| ログイン | 利用者名 + パスワード。BCryptで検証 |
| 多要素認証(MFA) | TOTP(RFC 6238)。QRコードで認証アプリへ登録 |
| トークン更新 | アクセストークンとリフレッシュトークンを分離 |
| ログアウト | リフレッシュトークンを失効させる |
| パスワード変更 | 12文字以上。**変更すると他端末のログインが解除される** |
| ログイン試行の制限 | 連続失敗で一時的に受付を止める(nginx側にも別の制限がある) |

### 役割

| 役割 | できること |
|---|---|
| 閲覧者 (Viewer) | 参照のみ。設定変更も復旧も承認もできない |
| 運用管理者 (OperatorAdmin) | 設定変更・復旧・承認・監査参照 |
| 実行専用 (SystemExecutor) | システム連携用。管理者専用の口は叩けない |

### MFA再認証

設定変更・復旧の実行・監査ログの参照は、役割に加えて
**MFAの認証が直近であること**を要求する。古い場合は役割が足りていても403を返す。

**権限の担保はAPI側で行う。**画面の出し分けは利便性のためであり、
画面を通さず直接APIを叩いても弾かれることをHTTP経由の試験で確認している。

### 接続元の制限

接続を許可するネットワーク範囲(CIDR)を登録できる。

### できないこと

- 利用者の**削除**はできない(無効化のみ)。監査ログが操作者IDを持つため、
  消すと過去の記録から誰の操作か辿れなくなる
- 自分自身の役割変更・無効化はできない(閉め出しを防ぐ)
- 最後の有効な運用管理者の降格・無効化はできない

## 3. 監視対象の管理

### 対応するテンプレート

| テンプレート | 監視する対象 | 収集できるもの |
|---|---|---|
| Docker Host | Dockerホスト全体 | コンテナ状態・ログ・CPU/メモリ・**ホストのディスク** |
| Docker Compose Application | 特定のComposeプロジェクト | コンテナ状態・ログ・CPU/メモリ |
| Web Site / API | HTTP/HTTPSの死活 | 応答コード・応答時間 |

### 対象ごとの設定

| 設定 | 内容 |
|---|---|
| 接続先 | Docker Socket ProxyのURL / チェックURL / node_exporterのURL |
| 資格情報 | Basic認証のパスワードなど。**暗号化して保存し、画面には返さない** |
| 収集間隔 | 対象ごとに指定 |
| 行う収集 | 5種から選ぶ(下記)。外したものは**API呼び出し自体を行わない** |
| 有効・無効 | 収集を止める |
| 自動復旧 | **初期値OFF** |
| 許可コンテナ | 操作してよいコンテナ名の一覧。**初期状態は空** |

### 選べる収集の単位

| 単位 | 内容 |
|---|---|
| コンテナ状態 | 一覧の取得と、停止コンテナのインシデント化 |
| ログ抜粋 | 停止コンテナと**稼働中コンテナ**のログ末尾 |
| CPU・メモリ使用率 | コンテナごと。1件あたり約1秒かかるため単独で外せる |
| ホストのディスク使用率 | node_exporterを設定した対象でのみ |
| HTTPヘルスチェック | 死活と応答時間 |

### その他

- 接続試験(対象を登録する前に到達性を確かめる)
- 対象の削除(関連データの件数を事前に提示する)
- 収集値の履歴表示(グラフ)

### できないこと

- Windows・ベアメタルの監視(Docker と HTTP に限る)
- SNMP・SSH経由の収集
- **ホストの実ディスクを埋める試験**(検証のためにホストを壊すことになるため)

## 4. 障害検知と診断

### 診断ルール

| 種別 | 判定するもの | 例 |
|---|---|---|
| 状態 (State) | 値が一覧に含まれるか | `containerState` が `exited` / `dead` |
| しきい値 (Threshold) | 数値の比較 | `memoryUsagePercent >= 90` |
| 正規表現 (Regex) | ログの一致 | `no space left on device` |

初期投入されるルールは6つ(コンテナ停止・HTTP応答不可・メモリ逼迫2種・ディスク逼迫2種)。
**版を上げて既定ルールが増えたときも、足りない分だけ後から投入される。**

### ルールの編集

- 画面から作成・更新・有効/無効の切り替え(運用管理者 + MFA再認証)
- 条件は自由記述のJSONではなく、**種別ごとのフォーム**で入力する
- **保存前に試験できる。**編集中の内容をそのまま評価し、保存済みルールと一緒に判定結果を見られる
- 正規表現は**実際に評価して時間を測る。**200ms以上かかるものは保存させない
- 推奨アクションIDは復旧の許可リストにあるものだけを受け付ける

### インシデント

| 機能 | 内容 |
|---|---|
| 障害署名による集約 | 同じ障害の繰り返しを1件にまとめ、発生回数を数える |
| 再発の検知 | 解決済みから再発するとOpenへ戻す |
| 診断の根拠 | どのルールにどの値が当たったかを文章で残す |
| 対応メモ | インシデントごとに記録を残す |
| 再診断 | 手動でやり直す |
| 再発履歴 | 同じ障害が過去にいつ起きたかを見る |
| ログ抜粋 | **秘密情報を伏せて**保存する |

### AI診断(任意)

- **初期状態は無効。**有効化は明示的な設定が必要
- ルールに当たらなかったものだけAIへ回す(費用と情報漏れを抑える)
- 送る前にログを匿名化・縮小する(IPアドレス・トークン・内部ホスト名を伏せる)
- 応答は厳格に検証し、**許可リストにあるアクションIDしか受け付けない**
- 時間あたり・日あたりの利用上限を設定できる

### できないこと

- **AIに自由記述のコマンドを実行させること**(そもそも経路が無い)
- 原因の自動特定(あくまで分類と候補の提示にとどまる)

## 5. 復旧

### 実行できる操作

| アクション | 危険度 | 承認 | 内容 |
|---|---|---|---|
| `RECHECK_HTTP_HEALTH` | Low | 不要 | 副作用なし。再確認するだけ |
| `RESTART_ALLOWED_CONTAINER` | Low | 不要 | 許可済みコンテナの再起動 |
| `START_ALLOWED_CONTAINER` | Medium | **必要** | 許可済みコンテナの開始 |
| `STOP_ALLOWED_CONTAINER` | Medium | **必要** | 許可済みコンテナの停止 |

**この4つ以外は実行できない。**AIが何を返しても、任意コマンドを通す経路が存在しない。

### 安全機構

| 機構 | 既定値 | 目的 |
|---|---|---|
| 対象別の許可リスト | 空 | 許可していないコンテナを操作しない |
| クールダウン | 10分 | 同じ対象・同じ操作を繰り返さない |
| 回数上限 | 2回/時 | 暴走を止める |
| サーキットブレーカー | 3回失敗で60分遮断 | 直らない障害で試行を続けない |
| 承認の有効期限 | 30分 | 古い承認で実行させない |
| 冪等キー | Medium操作で必須 | 二重実行を防ぐ |
| 実行直前の再検証 | — | 受付時の判断を信用しない |
| 復旧後ヘルスチェック | — | 直ったかを確かめる |

副作用のないLow操作(`RECHECK_HTTP_HEALTH`)は回数制限の対象外。

### 自動復旧

**6条件をすべて満たすときだけ動く。**

1. 対象で自動復旧が有効(初期値OFF)
2. 診断が推奨アクションを持ち、対象の能力で許可されている
3. Low危険度かつ承認不要(**Medium以上は自動実行しない**)
4. 操作対象が対象別の許可リストに含まれる
5. クールダウン・回数上限・サーキットブレーカーを通過
6. 実行直前の再検証を通過

**稼働中コンテナのログ検知からは自動復旧を呼ばない。**
ログは監視対象の側が自由に書ける値であり、これを引き金にすると
ログに書き込める者が稼働中のコンテナを再起動させられるため。

条件を満たさず止めた場合、**理由を監査に残す。**

### 承認

Medium以上の操作は、運用管理者の承認 + MFA再認証を要求する。

### できないこと

- 設定ファイルの書き換え・パッケージ更新・再デプロイ
- ホストへのコマンド実行(Docker APIの操作に限る)
- ディスク逼迫時の自動的なファイル削除(**消してよいものを決められるのは人だけ**)

## 6. 通知

| 機能 | 内容 |
|---|---|
| メール通知 | SMTP。STARTTLS対応 |
| Push通知 | Firebase Cloud Messaging(PWA) |
| 深刻度の下限 | この深刻度以上を通知する |
| 再通知の間隔 | 同じ事象はこの間隔内でまとめる |
| テスト通知 | **本物の障害を待たずに設定を確認できる** |
| 未読管理 | 通知一覧と未読件数 |
| 端末の失効 | Push送信の連続失敗が続いた端末を自動で失効させる |

**通知は初期状態で無効。**設定するまで何も送られない。
有効なのに宛先が空、という状態は保存できない。

テスト通知の宛先は**保存済みのものだけ**を使う(踏み台にされるため、画面から任意の宛先を指定できない)。

### メンテナンス期間

計画停止中は**通知せず、自動復旧も行わない。**対象と期間を指定して登録する。

## 8. 監査

| 機能 | 内容 |
|---|---|
| 記録する項目 | 操作者・IPアドレス・User-Agent・対象・操作・結果・時刻・変更前後 |
| 記録する操作 | 設定変更・復旧・承認・利用者管理・秘密値の変更・バックアップ・復元 |
| 絞り込み | 操作・対象・操作者・期間・結果 |
| CSV取り出し | 絞り込んだ結果をそのまま出す。**取り出したこと自体も監査に残る** |
| 保持期間 | **90日以上を強制**(痕跡を消すために期間を縮める操作を成立させないため) |

失敗した操作も記録する。「なぜ実行しなかったか」が残ることを重視している。

## 9. 設定

| 分類 | 内容 |
|---|---|
| 一般 | システム名・既定言語 |
| 保持期間 | 収集値・ログ・インシデント・監査ログ。削除件数を事前に確認できる |
| 秘密情報 | SMTPパスワード・AI APIキー・バックアップの鍵。**暗号化して保存し、値は決して返さない** |
| 許可ネットワーク | 接続を許可するCIDR |
| AI | 有効/無効・時間あたり/日あたりの上限 |

秘密情報は画面に「設定済み」とだけ表示される。
API応答・監査ログ・アプリログのいずれにも値が出ないことを試験で確認している。

## 10. バックアップと復元

### 取得

| 機能 | 内容 |
|---|---|
| 保存先 | S3互換(MinIO / NAS) |
| 暗号化 | **AES-256-GCM。平文を保存先へ送らない** |
| 定期実行 | 既定で毎日2時 |
| 手動実行 | 画面から |
| 世代管理 | 保持する世代数を超えた分を削除 |
| 実行履歴 | 成功・失敗と理由 |
| 失敗の通知 | High深刻度で通知する |

保存先が未設定なら、**黙って成功せず理由を残して失敗する。**

### 復元

| 機能 | 内容 |
|---|---|
| 世代の一覧 | 保存先にある世代を新しい順に |
| 下見 | **何も変更せず**、種別ごとに「追加・更新・変更なし・バックアップに無い」を返す |
| 実行 | 管理者 + MFA再認証。キーの再指定を確認として求める |
| 取り出す道具 | `scripts/restore-backup.py`(標準ライブラリのみで動く) |

**復元で戻すもの:** 設定・許可ネットワーク・監視対象とプロファイル・診断ルール

**復元で戻さないもの:**

| 戻さないもの | 理由 |
|---|---|
| 利用者 | パスワードハッシュが無く復元しても誰もログインできない。さらに降格した利用者を戻せると**復元が権限昇格の手段になる** |
| 自動復旧の有無・許可コンテナ | バックアップに含めない。**復元で自動実行の範囲が広がることを原理的に起こさない** |
| バックアップに無いもの | **消さない。**バックアップ以後に作った対象が消えるのを避ける |
| 収集値・インシデント・監査ログ | 対象外。`mysqldump` からの復元を使う |

## 11. 運用支援

| 機能 | 内容 |
|---|---|
| 自己監視 | 収集が届いていない対象を検出する(Worker停止から約240秒で表示) |
| 運用実績 | 検知から通知までの時間、自動復旧の成功率、安全機構が止めた理由 |
| ヘルスチェック | `live`(プロセス) / `ready`(DB接続まで) |
| 保持期間の自動削除 | 既定で毎日3時 |

自動復旧の成功率は「成功 ÷ (成功 + 失敗)」で計算する。
安全機構が止めた分は分母に入れない(入れると、安全に止めるほど成功率が下がる)。

## 13. サービスの展開(v1.0以降)

テンプレートからコンテナを展開する。**第2層(人が明示的に起動する運用操作)。**

| 機能 | 内容 |
|---|---|
| テンプレート一覧 | 組み込み5種(Uptime Kuma / Gitea / Vaultwarden / Redis / nginx) |
| 下見 | **何も作らず**、作られるコンテナ・ポート・ボリュームを示す |
| 展開 | イメージ取得 → ボリューム作成 → コンテナ作成。管理者 + MFA再認証 + 名前の確認 |
| 削除 | **稼働中は削除しない。**停止してから行う |
| 展開履歴 | いつ・誰が・どの版を展開したか |

### テンプレートで表現できないこと

**Composeファイルを丸ごと受け取る形にはしていない。**
Composeを受け取ると特権・ホストのマウント・任意のネットワーク設定まで指定でき、
テンプレートを登録できる者がホストを取れる。

展開できる形を「1コンテナ + 環境変数 + ポート + 名前付きボリューム」に限り、
危険な指定を**そもそも表現できないようにしてある。**

| 表現できないもの | 理由 |
|---|---|
| 特権コンテナ | 常に `Privileged: false` を送る |
| ホストのパスのマウント | 名前付きボリュームだけ。入力に `/etc` と書いてもボリューム名になる |
| `latest` のイメージ | 同じテンプレートから展開しても別のものが動く |
| 1024未満のポート | SSHなどを塞がせない |
| 8080 / 3306 などの予約ポート | このシステム自身と復旧手段を守る |

秘密値の入力は**下見にも展開記録にも監査にも残さない**(項目名だけ示す)。

## 14. 実装していないもの

意図的に実装していない項目。理由とともに記録する。

| 項目 | 理由 |
|---|---|
| TLS(HTTPS) | 自宅LAN内に閉じる前提。証明書の更新を運用に持ち込まない。公開する場合は前段にTLS終端を置く |
| CPU使用率の初期ルール | ビルドや動画変換のように100%が正常な使い方のコンテナは珍しくない。既定で入れると正常な稼働をインシデントにし続ける |
| 自分自身のハングからの自動復帰 | Docker Composeは`unhealthy`なコンテナを再起動しない。外部の監視役が要る(**設計上の限界として記録**) |
| 利用者の削除 | 監査ログから操作者を辿れなくなる |
| 監視対象の自動発見 | 意図しない対象を監視し始めるのを避ける |
| 複数テナント | 個人・小規模の運用を想定している |
