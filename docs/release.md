# リリース手順

自宅サーバーへ配置・更新するときの手順。**手を止めて確認する箇所を明示する。**

## 前提

- Docker / Docker Compose が使えること
- 外部へ公開するのは nginx の `HTTP_PORT`(既定8080)だけであること
- 既存の別システムとは独立したComposeプロジェクト(`server-operations`)であること

### 通信の暗号化についての判断

**このシステムは平文HTTPで待ち受ける。** 自宅LAN内に閉じて使う前提で、
TLS証明書の更新を運用に持ち込まない判断をしている。

そのため次が前提になる。守れないならこの構成のまま使わないこと。

- **LANの外へ公開しない。**ルーターでポート転送しない
- LAN内に信用できない端末を置かない

**インターネットから触れるようにする場合は、前段にTLS終端を置く。**
JWTとパスワードが平文で流れるため、この前提が崩れると認証情報がそのまま読まれる。
前段を置く場合は、nginxへ `X-Forwarded-For` を正しく渡すこと
(監査ログのIPアドレスがその値から決まる)。

## 1. リリース前の確認

### 自動試験がすべて通っていること

```bash
cd server && dotnet test
cd client-web && npm run test:unit -- --run && npm run type-check && npm run lint && npm run build
```

CIが緑であることをもって代えてもよい。

### イメージのタグが固定されていること

`latest` だけを使う運用はしない。`deploy/docker-compose.yml` で使う外部イメージは
すべて版を指定していることを確認する。

```bash
grep -n 'image:' deploy/docker-compose.yml deploy/lab-aioops/docker-compose.yml
```

期待する状態の例:

- `nginx:1.27-alpine`
- `mysql:8.4`
- `node:22-alpine`(ビルド用)

`:latest` や版の無い指定が現れたら、リリースを止めて版を固定する。

### 秘密情報がコミットされていないこと

```bash
git status --short           # .env が現れないこと
grep -rn 'BEGIN PRIVATE KEY\|password=' --include='*.json' --include='*.yml' . | grep -v node_modules
```

`.env` はGit管理しない。実際のIPアドレス・トークン・パスワードをコミットしない。

### 依存の版と脆弱性

- **EF Core は 9.0 で固定する。10.x へ更新しない。**
- 依存を上げたときは、移行(マイグレーション)の生成物に差分が出ていないか確認する

推移的な依存も含めて脆弱性を確認する。

```bash
cd server && dotnet list package --include-transitive --vulnerable
```

`./scripts/check-release-guards.sh` でも同じ確認を行う(CIでも実行される)。
実際には通らないコードパスであっても、依存として残さない方針とする。

## 2. 初回の配置

```bash
cd deploy
cp .env.example .env
```

`.env` を編集し、**ダミー値をすべて実際の値へ変える**。

| 変数 | 注意 |
|---|---|
| `MYSQL_ROOT_PASSWORD` / `MYSQL_PASSWORD` | 使い回さない |
| `JWT_SIGNING_KEY` | 32文字以上。`openssl rand -base64 48` で作る |
| `INITIAL_ADMIN_PASSWORD` | 12文字以上。**初回起動後に `.env` から消す** |
| `VITE_FIREBASE_*` | Push通知を使う場合のみ。未設定なら通知は「未設定」として扱われる |

起動:

```bash
docker compose up -d --build
```

確認:

```bash
docker compose ps                             # すべて healthy になること
curl http://localhost:8080/api/health/live    # liveness(プロセスが応答するか)
curl http://localhost:8080/api/health/ready   # readiness(DB接続まで確認)
curl -o /dev/null -w '%{http_code}\n' http://localhost:8080/api/v1/me   # 401 が返ること
```

最後の1つは**未認証で401が返ること**を確かめるためのもの。200が返るなら認証が効いていない。

`live` と `ready` は役割が違う。`live` はプロセスが応答するかだけを見る
(DBが落ちただけで再起動しても直らないため、依存を混ぜない)。
`ready` はDBへ接続できるかまで確かめる。**MySQLを止めた状態で `ready` が
200を返すなら、確認になっていない。**

コンテナの healthcheck は `live` を見る。ハングしたAPIは
`restart: unless-stopped` だけでは検知できない(プロセスは生きているため)。

### 初回ログイン後にすること

順番が重要。**MFAを設定するまで管理操作は一切できない。**
設定変更・復旧の実行・監査ログの参照は、MFAが有効で直近に認証していることを要求する。

1. 初期管理者でログインする
2. ヘッダーの利用者名から**アカウント画面**を開く
3. **MFAを設定する** — QRコードを認証アプリで読み取り、コードを入力して有効にする
4. 同じ画面で**パスワードを変更する**(12文字以上)。
   変更すると他の端末のログインは解除される
5. `.env` から `INITIAL_ADMIN_PASSWORD` を消す
6. 接続を許可するネットワーク範囲(CIDR)を登録する
7. 監視対象を登録し、接続試験が通ることを確かめる
8. **通知**と**バックアップの保存先**を設定する(後述)
9. **自動復旧は既定でOFF。**有効にする場合は、対象ごとに許可コンテナを先に設定する

管理操作で403が返る場合、まずアカウント画面でMFAの状態を確認する。
MFAの認証が古くなっている場合も403になるため、再度ログインし直す。

### 通知の設定

設定 → 通知。**通知は既定で無効。**設定するまで何も送られない。

1. **秘密情報**でSMTPパスワードを登録する(`smtp-password`)。
   Push通知を使う場合は `fcm-service-account` も登録する
2. 通知の画面で、通知する重大度・再通知の間隔を決める
3. メール通知を使う場合は、SMTPサーバー・ポート・差出人アドレス・宛先を入れて保存する

SMTPサーバーは**ホスト名またはIPアドレスだけ**を指定する。URLは受け付けない。
localhost・リンクローカル・メタデータIP宛は登録できない。

メール通知を有効にしたままSMTPサーバーや宛先が空だと保存は拒否される。
「有効なのに送れない」状態を作らないため。設定途中の状態は無効のまま保存できる。

保存したら「テスト通知を送る」で実際に届くことを確かめる。
**本物の障害を待たずに設定を確認できる唯一の手段。**宛先は保存済みのものだけを使い、
画面から任意の宛先を指定することはできない(踏み台にされるため)。
送信したことは監査に残る。

### 利用者の追加

利用者 → 利用者を追加。**役割は3つある。**

| 役割 | できること |
|---|---|
| 閲覧者 | 参照のみ。設定変更も復旧も承認もできない |
| 運用管理者 | 設定変更・復旧・承認・監査参照(MFA再認証が必要) |
| 実行専用 | システム連携用。管理者専用の口は叩けない |

追加した利用者には初期パスワードを渡し、**最初のログイン後にアカウント画面で
本人に変更させる**。管理操作を任せる場合はMFAの設定も必要になる。

**利用者は削除できない。**監査ログは操作者IDを持つため、消すと過去の記録から
誰の操作か辿れなくなる。使わなくなった利用者は無効にする(以後ログインできなくなり、
既存のセッションも切れる)。

次の操作は画面でもAPIでも拒否される。

- 自分自身の役割を変える(降格すると元へ戻す手段を失う)
- 自分自身を無効にする(その場で閉め出される)
- 最後の有効な運用管理者を降格・無効にする(誰も設定を変えられなくなる)

#### MFAを設定した端末を失ったとき

利用者 → 該当の行 → MFAをリセット。

**この操作自体が乗っ取りの経路になりうる。**そのため次を必ず行う。

- 運用管理者 + MFA再認証を要求する
- 対象の**全セッションを失効**させ、再ログインからやり直させる
- 誰がいつ誰のMFAをリセットしたかを監査に残す(`user.mfa.reset`)

自分のMFAはこの口ではリセットできない。アカウント画面から再設定する。

### 行う収集を絞りたいとき

監視対象 → 該当の対象 → 行う収集。

外した収集は**呼び出しそのものを行わない**。
例えば「停止コンテナのログ抜粋」を外すと、コンテナログのAPIを叩かなくなる。
ログに出したくない情報がある対象で使う。

- すべて外すとテンプレートの既定に戻る。**収集を止めたいなら「監視する」を外す**
- 「推奨する監視項目」は案内の文章で、選択肢ではない

**「CPU・メモリ使用率」だけは他より重い。**稼働中のコンテナ1件につき
Docker APIを別に呼び、正しい使用率を出すために約1秒待つ。
1回の収集で測るのは20件までで、それを超えた分は測らない(件数は収集値に残る)。
対象のコンテナが多い場合や、Docker APIへの負荷を抑えたい場合はここを外す。

なお使用率はコンテナごとの値のため、「コンテナの状態」を外していても
コンテナ一覧の取得だけは行われる。どのコンテナがあるかを知る必要があるため。

### リソース使用率のしきい値で検知したいとき

診断ルール → 「メモリ逼迫(使用率)」。既定では90%以上で作られる。

しきい値ルールは**それ自体がインシデントを作る**。
条件を緩めると、正常に動いているコンテナのインシデントが毎回の収集で作られる。

- **CPU使用率の初期ルールは置いていない。**ビルドや動画変換のように、
  100%が正常な使い方であるコンテナは珍しくないため。必要な対象にだけ足す
- **使用率が取れなかったコンテナは判定しない。**
  値が無いことを「しきい値を下回っている」と読み替えると逼迫を見逃す
- 使用率の逼迫では**自動復旧を試みない。**
  使用率が高いだけでは何を再起動すれば直るかが定まらないため、判断を人に残す

### ホストのディスク使用率を見たいとき

Docker APIはホストのファイルシステム容量を返さないため、
**監視対象のホスト側に node_exporter が要る。**

1. 監視対象のホストで node_exporter を起動する(既定ポート9100)
2. 監視対象 → 該当の対象 → 「ホストメトリクスURL」に
   `http://<ホスト>:9100/metrics` を入れて保存
3. 「行う収集」で「ホストのディスク使用率」が入っていることを確認する

**URLを入れなければ何も起きない。**設定していない対象で失敗を積み上げない。

- 読むのは `node_filesystem_*` だけで、**GETするだけ・ホスト上では何も実行しない**
- URLは保存時に検証する(http/httpsのみ、localhost・リンクローカル・
  メタデータIPは登録できない)。接続の直前にも同じ基準で確かめる
- 使用率は `df` と同じ計算にしてある。ext4などのroot予備領域を除いた
  「実際に書ける量」を基準にするため、`df` の Use% と一致する
- tmpfsやoverlayは除く(実ディスクの残量を表さないため)
- 既定ルール「ディスク逼迫(使用率)」は **85%**。メモリの90%より低い。
  メモリは解放されれば戻るが、ディスクは自然には減らないため
- ファイルシステムごとに別のインシデントになる。
  `/` と `/mnt/data` では消すべきものが違う
- ディスク逼迫でも**自動復旧は試みない。**
  コンテナを再起動しても容量は戻らず、消してよいものを決められるのは人だけ

**Composeアプリの対象では扱わない。**ホストのディスクはプロジェクト単位の値ではなく、
同じホストの対象ごとに同じ数値のインシデントが並んでしまうため。
Dockerホストの対象で設定する。

### 監視が届いているかの確認

ダッシュボードの最上部に「**監視が届いていない対象があります**」が出ていないことを確認する。

これは自己監視の表示で、収集が止まっている対象を挙げる。
**インシデントが0件であることは、異常が無いことを意味しない。**
Workerが死んでいても、対象へ到達できなくなっていても、同じく0件になる。
その区別を付けるための表示なので、0件だけを見て安心しないこと。

出ている場合に見る順番:

1. `docker compose ps` で worker が healthy か
2. `docker compose logs --tail=100 worker` に例外が出ていないか
3. 対象の詳細画面で「接続を試す」が通るか

### メンテナンス期間(計画停止の前に)

メンテナンス → 期間を登録する。

サーバーを自分で更新・再起動する前に登録しておくと、その作業を障害として
通知したり、自動復旧が動いて作業を邪魔したりしなくなる。

- **検知そのものは止まらない。**期間中に起きたことはインシデントとして残る
- 通知と自動復旧のどちらを止めるかは個別に選べる。両方止めない期間は登録できない
- 対象を選ばなければすべての監視対象に効く
- 登録と取り消しはどちらも監査に残る

期間中に自動復旧を止めた場合、監査ログの `recovery.auto.denied` に理由が残る。
「なぜ自動復旧が動かなかったのか」はここで確認できる。

### バックアップの保存先

設定 → バックアップ → バックアップの保存先。**定期バックアップは既定で無効。**

1. **秘密情報**で `backup-secret-key` を登録する
2. 保存先のURL(S3互換。MinIOなど)・バケット名・保持する世代数を入れて保存する
3. 「接続を試す」で到達できることを確かめる
4. 「定期バックアップを行う」を有効にして保存する

保存先も接続先の検証を通る必要がある。localhostやリンクローカルのアドレスは登録できない。
有効にしたまま保存先やバケット名が空だと保存は拒否される。

#### 画面のバックアップに何が入るか

**画面から取るバックアップと、DBの完全なダンプは別物。**取り違えると復元できない。

| | 画面のバックアップ | `mysqldump` |
|---|---|---|
| 設定・監視対象・診断ルール | 含む | 含む |
| 収集値・インシデント・監査ログ | **含まない** | 含む |
| 暗号化済みの秘密値 | **含まない** | 含む |
| 復元 | **未実装(手作業で入れ直す)** | `mysql` へ流し込む |

画面のバックアップは「設定を書き写したもの」であり、
**そこから丸ごと戻す機能は実装していない。**現状は中身を見て手で入れ直すことになる。

**移行を含む更新の切り戻しには `mysqldump` を使う。**画面のバックアップでは戻せない。

秘密値が含まれないのは意図した設計で、保存先が漏れても認証情報は漏れない。
その代わり、復元後は秘密情報(SMTPパスワード・APIキー等)を**登録し直す必要がある**。

### 監視対象を消すとき

監視対象 → 該当の対象 → 監視対象の削除。

**削除すると、その対象の収集値・インシデント・診断・復旧履歴も一緒に消える。
元には戻せない。** 削除前に「何が消えるか確認する」で件数を見ること。

監視中の対象は削除できない。先に「監視する」を外す。

**監査ログは消えない。**誰がいつ何をしたかの記録は残る。
削除操作そのものも `target.delete` として、消えた件数つきで記録される。

試験用に登録した対象を片付ける用途を想定している。
運用中の対象を整理したいだけなら、削除ではなく「監視する」を外すほうが安全。

## 3. 更新

```bash
cd deploy
git pull
docker compose up -d --build
```

DBの移行はAPI起動時に自動で適用される(`Database__AutoMigrate=true`)。

### 更新前に取るもの

**移行を伴う更新の前は必ずバックアップを取る。**

```bash
# 画面から: 設定 → バックアップ → いま実行する
# または直接:
docker compose exec mysql mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" \
  --single-transaction --routines --default-character-set=utf8mb4 \
  "$MYSQL_DATABASE" > backup-$(date +%Y%m%d-%H%M%S).sql
```

### 更新後の確認

```bash
docker compose ps                                  # すべて healthy / running
curl http://localhost:8080/api/health/ready        # readiness
docker compose logs --tail=50 api worker           # 例外が出ていないこと
```

画面で次を確認する。

1. ログインできること
2. ダッシュボードに監視対象が出ること
3. 監査ログに更新前後の記録が残っていること

## 4. 切り戻し

更新後に問題が起きた場合。

```bash
cd deploy
git checkout <前のタグまたはコミット>
docker compose up -d --build
```

**DBの移行は自動では戻らない。** 移行を含む更新を切り戻すときは、
更新前に取ったバックアップから復元する。

```bash
docker compose exec -T mysql mysql -u root -p"$MYSQL_ROOT_PASSWORD" \
  "$MYSQL_DATABASE" < backup-YYYYmmdd-HHMMSS.sql
```

復元は既存データを置き換える。**実行前に、いま入っているデータを失ってよいか必ず確認する。**

## 5. 配置後に効いていることを確かめる安全条件

リリースのたびに、次が保たれていることを確認する。

| 確認すること | 見かた |
|---|---|
| 外部に開いているポートが1つだけ | `docker compose ps` の PORTS 欄 |
| MySQL・API・Workerが外部へ出ていない | 同上。ポート公開が無いこと |
| Dockerソケットがweb/apiに渡っていない | `docker compose config` で `docker.sock` の行を確認 |
| 未認証でAPIが叩けない | `curl` で保護された口が401を返すこと |
| 秘密値が画面・API応答に出ない | 設定画面の秘密情報が「設定済み」とだけ出ること |
| 自動復旧の既定がOFF | 新規に登録した対象で自動復旧が無効であること |
| 監査ログが残っている | 監査ログ画面に配置作業前後の記録があること |
| すべてのコンテナに healthcheck がある | `docker compose ps` の STATUS が healthy であること |
| ログに上限がある | `docker inspect` の LogConfig に max-size があること |
| ログイン試行が制限される | 誤ったパスワードを6回続けて429が返ること |
| 監査ログの保持が90日以上 | 設定 → 保持期間。それ未満は保存できない |
| 監視が届いている | ダッシュボードに「監視が届いていない対象」が出ていないこと |

Dockerソケットの確認は特に重要で、**web/apiコンテナへ直接渡してはならない**。
Dockerへの接続はSocket Proxy経由に限る。

## 6. 定期的に見るもの

| 頻度 | 内容 |
|---|---|
| 毎日 | ダッシュボードに「監視が届いていない対象」が出ていないこと |
| 毎日 | 通知・未解決インシデント |
| 毎週 | 運用実績(検知から通知までの時間・自動実行を止めた理由) |
| 毎週 | バックアップが成功しているか(設定 → バックアップ → 実行履歴) |
| 毎月 | 監査ログの見直し。AI利用量が上限に対してどうか |
| 随時 | 依存の脆弱性情報。ただしEF Coreは9.0で固定する |

バックアップは**取れているだけでは足りない**。復元できることを定期的に確かめる。
