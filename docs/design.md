# 設計書

自律型サーバー運用支援システムの、背景・目的・設計判断をまとめる。

手順書(`release.md`)と検証手順(`verification.md`)が「どう使うか」を書くのに対し、
ここは**「なぜそう作ったか」**を書く。

---

## 1. 背景と課題

### 個人が運用するサーバーの実情

自宅サーバーやVPSでDockerを使う個人・小規模な運用では、次が同時に起きる。

- **見ていない時間が長い。** 常時監視する人手が無い
- **落ちても気づかない。** 気づくのは使おうとしたときで、それまで止まったまま
- **原因を調べる知識と時間が要る。** ログを読み、何が起きたかを判断する
- **同じ障害が繰り返される。** 前回どう直したかが残らない

Zabbix や Prometheus のような監視基盤は「検知」までは解決するが、
**検知の後に何が起きているかを判断し、安全に直す**ところは人に残る。

### この研究で扱う範囲

「検知」から「復旧」までを、**人が見ていない時間帯でも安全に進める**仕組みを作る。

ただし「全自動で何でも直す」ことは目指さない。**間違った自動操作は、
障害そのものより重い被害を出す。**そのため本システムの中心は、
自動化の範囲をどう絞るかという設計にある。

---

## 2. 目的

| # | 目的 |
|---|---|
| 1 | Dockerコンテナ・HTTPサービス・ホスト資源の状態を定期的に収集する |
| 2 | 収集値から障害を検知し、**根拠つきで**分類する |
| 3 | ルールで判断できないものだけ外部AIへ回す(費用と情報漏れを抑える) |
| 4 | 安全条件をすべて満たす場合に限り、低危険度の復旧を自動実行する |
| 5 | 危険な操作は人の承認を要求し、すべての操作を監査に残す |
| 6 | 自宅LAN内で完結し、外部サービスへの依存を最小にする |

---

## 3. 対象と前提

### 対象

- Dockerで動くコンテナ(状態・再起動回数・ログ・CPU/メモリ使用率)
- HTTPで死活を確認できるサービス
- ホストのファイルシステム使用率(node_exporter経由)

### 前提

**自宅LAN内に閉じて使う。**平文HTTPで待ち受け、TLS証明書の更新を運用に持ち込まない。
インターネットへ公開する場合は前段にTLS終端を置く必要がある
(この判断とその条件は `release.md` に明記している)。

## 4. システム構成

### 全体

```
                    LAN
  ┌──────────────────────────────────────────┐
  │                                          │
  │   [利用者のブラウザ]                       │
  │        │ HTTP 8080(唯一の公開ポート)      │
  │        ▼                                 │
  │   ┌─────────┐                            │
  │   │  nginx  │ リバースプロキシ            │
  │   └────┬────┘ セキュリティヘッダ          │
  │        │       ログイン試行の制限          │
  │   ┌────┴─────┬──────────┐                │
  │   ▼          ▼          │                │
  │ [web]      [api]        │                │
  │  SPA    ASP.NET Core    │                │
  │            │            │                │
  │            ▼            ▼                │
  │        ┌───────┐   ┌────────┐            │
  │        │ MySQL │◀──│ worker │            │
  │        └───────┘   └───┬────┘            │
  │                        │ 収集・復旧       │
  │        ┌───────────────┼──────────┐      │
  │        ▼               ▼          ▼      │
  │  [Socket Proxy]  [監視対象HTTP] [node_   │
  │        │                        exporter]│
  │        ▼                                 │
  │   Docker daemon                          │
  └──────────────────────────────────────────┘
                     │ 必要時のみ
                     ▼
              [外部AI(Gemini)]
```

### 各要素の役割

| 要素 | 役割 |
|---|---|
| nginx | 唯一の公開口。リバースプロキシ、セキュリティヘッダ、ログイン試行の制限 |
| web | Vue 3のSPA。静的配信のみ |
| api | 認証・認可・設定・参照系。**収集も復旧の実行も行わない** |
| worker | 定期収集・診断・自動復旧の実行。Hangfireでジョブを管理 |
| MySQL | 収集値・インシデント・診断・監査ログ |
| Socket Proxy | Dockerへの唯一の経路。**web/apiにdocker.sockを渡さない** |

### 技術選定

| 領域 | 採用 | 理由 |
|---|---|---|
| Backend | C# / ASP.NET Core (.NET 10) | 静的型付けで、権限や危険度の取り違えをコンパイル時に落とせる |
| ORM | EF Core 9.0 | **9.0で固定。**10.xは移行の生成物が変わるため上げない |
| ジョブ | Hangfire | 対象ごとの定期実行と、キュー分離(復旧を収集より優先)が要るため |
| Frontend | Vue 3 / TypeScript / Vite | 画面数に対して構成が軽く、型を通せる |
| DB | MySQL 8.4 | 既存環境と揃える。日時は `datetime(6)` で統一 |

## 5. 中心にある設計判断

このシステムの本体は「監視」ではなく**「どこまで自動でやるかの線引き」**にある。
以下は、その線をどこに引いたかの記録である。

### 5.1 自由記述のコマンドを実行する経路を作らない

AIに診断させる以上、**AIの応答が操作につながる経路は攻撃対象になる。**
収集したログには、監視対象の側が任意の文字列を書き込める。

そこで、**実行できる操作をあらかじめ4つに固定した。**

| アクションID | 危険度 | 承認 | 内容 |
|---|---|---|---|
| `RECHECK_HTTP_HEALTH` | Low | 不要 | 副作用なし。再確認するだけ |
| `RESTART_ALLOWED_CONTAINER` | Low | 不要 | 許可済みコンテナの再起動 |
| `START_ALLOWED_CONTAINER` | Medium | **必要** | 許可済みコンテナの開始 |
| `STOP_ALLOWED_CONTAINER` | Medium | **必要** | 許可済みコンテナの停止 |

AIの応答は厳格に検証し、**この一覧に無いアクションIDは受け付けない。**
そのため、AIが何を返しても任意コマンドは実行できない。
「危険なコマンドを弾く」のではなく、**そもそも通す経路が無い**という形にしてある。

### 5.2 自動実行は6つの条件をすべて満たすときだけ

自動復旧が動くのは、次を**すべて**満たす場合に限る。

1. 対象で自動復旧が有効(**初期値はOFF**)
2. 診断が推奨アクションを持ち、対象の能力で許可されている
3. アクションがLow危険度かつ承認不要(**Medium以上は自動実行しない**)
4. 操作対象コンテナが**対象別の許可リスト**に含まれる(初期状態は空)
5. クールダウン・回数上限・サーキットブレーカーを通過する
6. 実行直前の再検証を通過する

条件を1つでも満たさなければ実行せず、**止めた理由を監査に残す。**
「何もしなかった」ではなく「なぜしなかったか」が残ることを重視した。

### 5.3 ログ由来の検知からは自動復旧を呼ばない

稼働中コンテナのログを走査して障害を検知するが、
**そこからは自動復旧を起動しない。**

ログの中身は監視対象の側が自由に書ける。これを自動実行の引き金にすると、
**ログに書き込める者が、稼働中のコンテナを再起動させられる。**
停止したコンテナを戻すのと、動いているものを止めるのは危険度が違う。

### 5.4 「0件だった」を成功と読み替えない

検証の判定で、材料が0件のときは「達成」と書かず「測定できず」と出す。

自動実行が1件も無い状態で「危険な操作をしなかった」と報告すると、
**何も起きていないだけなのに検証したことになる。**
実際、開発の途中でこの読み替えが起きていた(後述)。

### 5.5 バックアップの復元を権限昇格の経路にしない

バックアップから復元する際、**利用者は復元しない。**

バックアップにパスワードハッシュが入っていないため復元しても誰もログインできず、
さらに降格・無効化した利用者を古いバックアップで元に戻せてしまうと、
**復元そのものが権限昇格の手段になる。**

同じ理由で、自動復旧の有無と許可コンテナはバックアップに含めていない。
**復元によって自動実行の範囲が広がることは原理的に起きない。**

### 5.6 権限は画面ではなくAPIで担保する

画面の出し分けは利便性のためであり、権限の担保はAPI側で行う。
画面を通さず直接APIを叩いても弾かれることを、HTTP経由の試験で確認している。

設定変更・復旧・監査参照は、役割に加えて**MFAの再認証が新しいこと**を要求する。

## 6. 障害検知の流れ

```
  収集(worker)
    ├─ Docker API      : コンテナ状態・ログ・CPU/メモリ使用率
    ├─ HTTP            : 死活と応答時間
    └─ node_exporter   : ホストのディスク使用率
         │
         ▼
  ルール判定(RuleEngine)
    ├─ 状態ルール      : containerState が exited/dead
    ├─ しきい値ルール  : memoryUsagePercent >= 90 など
    └─ 正規表現ルール  : ログに "no space left on device" など
         │
    ┌────┴────┐
    │         │
  一致        一致しない
    │         │
    ▼         ▼
  診断      外部AIへ(有効な場合のみ)
    │         │ 匿名化・縮小して送信
    │         │ 応答は許可リストで検証
    └────┬────┘
         ▼
    インシデント(障害署名で集約)
         │
         ▼
    自動復旧の判定(5.2の6条件)
         │
    ┌────┴────┐
   実行      止める + 理由を監査へ
```

### 障害署名による集約

同じ障害が繰り返し検知されても、インシデントは1件にまとめる。
署名は「対象ID + サービス名 + 分類 + 正規化したログ」から算出する。

ログの正規化では数値を伏せる。タイムスタンプやプロセスIDが変わるだけで
別の障害として扱われるのを防ぐため。

**稼働中コンテナのログ検知では、一致した部分だけを署名に使う。**
ログ末尾をそのまま使うと行が流れるたびに署名が変わり、
収集のたびに新しいインシデントが積み上がる。

## 7. 検証の設計

検証は2層に分けた。

| 層 | 保証する範囲 | 実行環境 |
|---|---|---|
| 自動試験 | 判断の筋道が仕様どおりか | CI(811件 + 278件) |
| 実環境試験 | 実際のコンテナ・ネットワークで動くか | 検証専用VM |

**自動試験は判断の筋道までしか保証しない。**
実際にコンテナが再起動するか、マイグレーションが通るか、
healthcheckが効くかは実環境でしか確かめられない。

この分離は結果的に正しかった。**自動試験780件がすべて緑の状態で、
配置すると起動しない不具合が4件あった**(後述)。

### 実環境試験の自動化

配置から成功基準の測定までを `scripts/lab-verify.sh` で通しで行う。
MFAの設定と監視対象の登録も自動で行う(管理操作にはMFA再認証が要るため、
これが無いと監視対象の登録すらできない)。

## 9. 動かして初めて分かったこと

**この研究で最も価値のある部分は、ここだと考えている。**

自動試験が全部緑でも見つからず、実際に配置して動かして初めて出た不具合を記録する。

### 9.1 配置できない(4件)

自動試験780件が通っている状態で、**1件でも残っていればシステムが起動しない**
不具合が4件あった。

- 行サイズ超過でマイグレーションが失敗する(utf8mb4は1文字4バイト)
- Workerのランタイム画像が違う(Data Protectionに aspnet が要る)
- Hangfireの定期ジョブにキューを直接指定していた
- Data Protectionの鍵が書けない(ボリュームがroot所有で作られる)

### 9.2 稼働中コンテナのログを一度も読んでいなかった

ログ抜粋は停止(`exited`/`dead`)コンテナからしか取得しておらず、
**動き続けたままエラーを出すコンテナのログは永久に読まれない**状態だった。

そのため、ディスク逼迫のシナリオ(tmpfsを満たす。コンテナは動き続ける)は
**構造的に検知不能**だった。ログ検知のルールは実質的に停止後にしか当たらない。

### 9.3 更新のたびにnginxが502を返す

`proxy_pass` にホスト名を直書きし `resolver` が無いため、
nginxは起動時に一度だけ名前解決して固定していた。

更新手順ではapiだけが作り直され、nginxは据え置かれる。
その結果**更新のたびに502になり、nginxを手で再起動するまで直らない。**

### 9.4 healthcheckが3サービスで常に失敗していた

5サービス中3つが起動直後から `unhealthy` のままだった。
「更新後の確認: すべて healthy」という手順は**一度も通らない状態**だった。

- nginx / web: `localhost` が `::1` に解決され、IPv4しか待ち受けていないため接続拒否
- worker: 心拍を書くサービスが条件分岐の反対側にあり、**実配置では一度も動いていなかった**

### 9.5 検証そのものが空振りしていた

**成功基準#6(プロンプト注入)が、一度も注入を試さずに「達成」と出ていた。**

原因は2つ重なっていた。

1. シナリオの出力が `docker compose exec` のセッションにしか出ず、
   収集が読むコンテナのログストリームに入っていなかった
2. 注入文はどのルールにも当たらないためインシデントが作られず、
   保存も診断もされない = AIへ渡る経路を通っていなかった

それにも関わらず判定は別の値(自動実行の件数)から導かれていたため、
何も試していないのに達成と表示されていた。

**「0件を達成と書かない」保護は用意してあったが、この基準だけ分母が違ったため効かなかった。**
守りを1つ入れただけでは足りず、どの判定がどの材料に依っているかを個別に確かめる必要がある。

### 9.6 「AAを目標に選んだ」配色が6箇所で未達

実測したところ、WCAG 2.2 AAに届いていない組み合わせが6件あった。

| 箇所 | 実測 | 必要 |
|---|---|---|
| 暗い配色の主ボタン(白文字 / 明るい青) | 2.34:1 | 4.5:1 |
| 入力欄とボタンの枠(明) | 2.08:1 | 3:1 |
| 深刻度「高」の帯 | 4.45:1 | 4.5:1 |

目視では気づけないため、42組の比率を試験で固定した。

## 10. 設計上の限界

直さずに記録した項目。

### healthcheckは検知するが、復旧はしない

ホストからapiのプロセスを停止させてハングを再現したところ、
91秒で `unhealthy` になったが、181秒経っても再起動されなかった。

**Docker Composeは `unhealthy` なコンテナを再起動しない。**
`restart: unless-stopped` はプロセスが終了したときにしか働かない。

つまり本システムは、**他のサービスのハングは検知・復旧できるが、
自分自身のハングからは自力で復帰できない。**
これを解決するには外部の監視役が要る。

### 収集データは設定のバックアップに含まれない

アプリのバックアップは設定・監視対象・診断ルールを対象とし、
インシデント・監査ログ・収集値は含まない。
これらを戻すには `mysqldump` 側の手順を使う。

### 未検証の項目

- Push通知の実機確認(Firebaseの設定値が必要)
- スクリーンリーダーでの確認(配色の比率は実測済み)
- 負荷試験・長時間運転

## 11. 結論

### 得られたもの

「検知から復旧まで」を人が見ていない時間帯でも進める仕組みを作り、
検証専用VMでの通し実行で成功基準9項目すべてを達成した。

自動化の範囲は、**実行できる操作を4つに固定し、
自動実行を6条件すべての通過に限る**ことで絞った。
この形にすると、AIが何を返しても任意コマンドを実行する経路が存在しない。

### 分かったこと

**自動試験は「判断の筋道」しか保証しない。**

780件が緑でも、行サイズ・画像の選択・ライブラリの制約・ファイルの所有者・
名前解決のタイミングは1つも見ていなかった。配置してみるまで、
これらは存在しないのと同じだった。

さらに踏み込むと、**検証そのものが空振りしていても気づけない。**
基準#6は一度も注入を試さずに「達成」と表示されていた。
検証を自動化したこと自体が、検証の空白を見えなくしていた。

自律的に運用を支援するシステムを作るうえで、
**「確かめたつもり」をどう潰すかが、機能を増やすことより重要**だった。
