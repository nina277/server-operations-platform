# 拡張の設計 — 二層の境界

卒業制作(`v1.0-graduation`)の後、監視以外の機能を足すための設計。

**この文書が決めるのは1つだけ。「無人で動く経路」と「人が起こす経路」の境界。**
ここを曖昧にしたまま機能を足すと、卒業制作の安全設計が空文になる。

---

## 1. なぜ境界が要るか

`v1.0` の安全性は、次の一文で説明できていた。

> 実行できる操作を4つに固定したから、AIが何を返しても任意コマンドを実行する経路が存在しない。

「いろんなことができる」を素朴に足すと、この主張が崩れる。
操作が増えれば、**ログに文字列を書き込める者が到達できる操作**も増えるためである。

一方で、個人利用のプラットフォームとして使うなら、
デプロイや定期タスクのような「危険だが必要な操作」は要る。

そこで**操作を危険度ではなく「誰が決めたか」で二層に分ける。**

---

## 2. 境界の定義

| | 第1層 自動操作 | 第2層 運用操作 |
|---|---|---|
| **誰が起動するか** | システム(無人) | **人が明示的に** |
| 引き金 | 診断結果・ルール一致 | 画面からの操作、または人が登録した予定 |
| 操作の範囲 | **4つに固定** | 追加できる |
| 危険度 | Low のみ | Low / Medium / High |
| 承認 | 不要(Lowのみのため) | 危険度に応じて要求 |
| AIの応答が届くか | **届く**(だから固定する) | **届かない** |

### 分ける基準は「危険度」ではなく「誰が決めたか」

危険度で分けると「Lowなら自動でよい」という話になり、
操作が増えるほど自動実行の面積も増える。

**無人で動くかどうかで分ける。**
人が画面の前で押した操作は、その人が結果を引き受ける。
無人で動く操作は誰も見ていない。だから後者だけを固定する。

---

## 3. 破ってはならない不変条件

```
第1層(自動)から第2層のアクションへ到達できない
```

具体的には次を保証する。

1. 診断の推奨アクション(`RecommendedActionId`)に指定できるのは**第1層のアクションだけ**
2. AIの応答から受け付けるアクションIDも**第1層だけ**
3. 診断ルールの推奨アクションに設定できるのも**第1層だけ**
4. 自動復旧の実行経路は、第2層のアクションIDを渡されたら**必ず拒否する**

**この4つは試験で固定する。**第2層に何を足しても、
「ログに書き込める者が到達できる操作」は増えない。

### 稼働中コンテナのログ検知は第1層にも入れない

`v1.0` で決めたとおり、ログ由来の検知からは自動復旧を呼ばない。
第2層を足してもこの判断は変えない。

---

## 4. 経路を2本に分ける

### 決めたこと

**監視用の狭い経路はそのまま残し、展開用の広い経路を別に立てる。**

| 経路 | 権限 | 使う機能 |
|---|---|---|
| `socket-proxy`(既存) | 参照 + start/stop/restart のみ | 収集・自動復旧(第1層) |
| `deploy-proxy`(新設) | イメージ・ボリューム・ネットワーク・コンテナ作成 | サービスの展開(第2層) |

### なぜ分けるか

**Docker APIへのフルアクセスは、ホストのrootと同義である。**
任意のイメージを privileged で起動できるため、実質的に何でもできる。

1本にまとめると、収集や自動復旧までがその広い権限で動くことになる。
経路を分ければ、**無人で動く第1層は従来どおり狭い権限のまま**でいられる。

これは第3節の不変条件と対になる。

```
第1層(無人) → 狭い経路  … 権限そのものが足りず、展開操作を行えない
第2層(人)   → 広い経路  … 人が明示的に起動したときだけ通る
```

境界をコードだけでなく**権限でも二重に守る。**
仮にコード側の判定を誤っても、第1層の経路には展開に必要な権限が無い。

### 失うもの

展開を行う以上、`deploy-proxy` を持つ経路は実質的にホストのrootである。
**卒業制作の「Dockerソケットを直接渡さない」という防御は、この経路については手放す。**
個人利用の管理プラットフォームとして意図的に選んだ判断であり、
監視だけを行う構成では従来の安全性が保たれる。

---

## 5. VM管理はProxmoxに委ねる

VM作成をlibvirtで自前実装せず、**Proxmox VE のREST APIを叩くアダプタ**として実装する。

### なぜか

このシステムの強みは仮想化そのものではなく、
**安全条件・承認・監査・通知を操作に被せる枠**にある。

VMのライフサイクル・スナップショット・バックアップはProxmoxが既に持っている。
1から作り直しても得るものが少なく、卒業制作1本分の労力がかかる。

Proxmoxを「監視対象かつ操作対象」として扱えば、
**Proxmoxの機能に承認と監査を被せられる。**これは既存のProxmox単体では得られない。

### 扱う操作(第2層)

| 操作 | 想定する危険度 |
|---|---|
| VMの一覧・状態の取得 | 参照 |
| VMの起動 | Low |
| VMの停止・再起動 | Medium |
| スナップショットの作成 | Low |
| **VMの作成** | High(確認を厚く) |
| VMの削除 | High |

---

## 6. 第2層で足すもの

### 6.1 Docker運用

画面から明示的に行う操作。

| 操作 | 想定する危険度 |
|---|---|
| イメージの取得(pull) | Low(副作用が小さい) |
| コンテナの作り直し(pull → recreate) | Medium |
| Composeプロジェクトの起動・停止・再起動 | Medium |
| コンテナの削除 | High(確認を厚く) |

いずれも**対象別の許可リストの内側**でのみ行う。
許可リストは第1層と共有する(操作してよい対象の定義は1つにする)。

### 6.2 定期タスク

**任意のシェルコマンドは実行しない。**
「いろんなことができる」を任意コマンドで実現すると、
このシステムが持つ意味(安全に絞ること)が無くなる。

代わりに、**登録済みのアクションを予定に沿って回す**形にする。

| 要素 | 内容 |
|---|---|
| 実行内容 | 第2層のアクション(1つ以上) |
| 予定 | cron式 |
| 承認点 | **登録するとき。**人がその時点で内容を承認する |
| 実行履歴 | 成功・失敗・所要時間 |
| 失敗時 | 通知する |
| 監査 | 登録・変更・削除・各実行を残す |

定期タスクは「人が登録した内容を、人が決めた時刻に回す」ものであり、
**システムが内容を決めることはない。**そのため第2層に属する。

---

## 7. 実装の順序

| 段階 | 内容 | 状態 |
|---|---|---|
| 0 | 二層の仕組みと不変条件の試験 | ✅ 完了 |
| 1 | 展開用の経路と、第2層のDocker操作 | ✅ 完了 |
| 2 | サービステンプレートからの展開 | ✅ 完了(画面は段階5) |
| 3 | Proxmoxアダプタ(VM管理) | — |
| 4 | 定期タスクの基盤 | — |
| 5 | 画面 | — |

段階0を先に済ませた。**枠を作る前に機能を足すと、後から境界を引き直せない。**

段階1・2を先に置くのは、①既存のテンプレート概念と安全機構をそのまま活かせる
②単体で完結して価値が出る ③VM作成より使用頻度が高い、の3点による。

---

## 8. この設計で失うもの

正直に書いておく。

- **操作が増えれば、人の誤操作の余地は増える。**
  第2層は人が起動するため、押し間違いは防げない。確認と監査で受ける
- **`v1.0` の「4つに固定」という一文では説明できなくなる。**
  今後は「無人で動く操作は4つに固定」と言う必要がある
- 第2層の操作は、対象の許可リストに依存する。
  許可リストを広く取ると危険度が上がる点は第1層と同じ
